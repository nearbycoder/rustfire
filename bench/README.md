# Benchmark protocol

Use **the same machine**, room fixture size, number of concurrent clients, request bodies, and duration for both servers. Run a warmup before recording results. Keep the server and load generator on separate machines when measuring high throughput. Record CPU, peak RSS, and response error rate alongside latency and throughput. Test at several concurrency levels and increase until the p95 latency or error rate crosses your service objective.

For the matched-fixture trial in `RESULTS.md`, build Rustfire with `cargo build --release`. Run the pinned upstream Campfire commit with Ruby 3.4.10, its locked gems, Redis, and `RAILS_ENV=production DISABLE_SSL=1` on localhost. The upstream Puma configuration automatically chooses its worker count; leave `WEB_CONCURRENCY` and `RAILS_MAX_THREADS` unset to reproduce the packaged-app baseline. Create the first administrator in each app, then stop both servers and seed disposable databases:

```sh
python bench/seed.py campfire /path/to/once-campfire/storage/db/production.sqlite3 --count 10000
python bench/seed.py rustfire /path/to/rustfire/data/compare.db --count 10000
```

The seed script uses the same text and client message IDs in both databases. It refuses a nonempty message table unless `--replace` is supplied. After a write warmup, restore the original fixture before the measured run. Confirm both servers use SQLite WAL and `PRAGMA synchronous=NORMAL`, and that `GET /rooms/1/messages` returns the latest 40 messages with status 200, before recording throughput.

For matched conditional message-list reads, run `cargo build --release` and `python bench/paired_message_cache.py`; add `--clients 32 128 256 512 --seconds 15 --campfire-workers 22` for the concurrent 304 sweep, and repeat with `--rustfire-first` to reverse trial order. The probe uses disposable databases and isolated Redis, seeds the same 40 ordered messages, checks default and cursor pages, weak ETags, Last-Modified, 200/304/204 responses, cache-control, and validator changes after a message update. It checks the parsed 200 message markup and eight CSRF-bearing boost forms per message after normalizing the tokens, fixture-specific names and room title, signed avatar URLs, and server origins. Add `--sample-dir /tmp/message-samples` to save the raw 200 bodies. Its Go client warms each connection and checks every measured 304 status, empty body hash, ETag, and Last-Modified. The two apps run serially on the same host as the client. The validators and raw 200 HTML bytes differ; this measures one cached read route, not full-page parity or whole-app capacity.

For rendered message-list reads on the same fixture, use `--full-clients 8 32 64 128 --seconds 5 --campfire-workers 22` and repeat with `--rustfire-first`. Every measured 200 response must retain its ETag and Last-Modified and contain all 40 message roots and 320 CSRF fields. The initial page also passes the parsed markup comparison before timing. This is one account repeatedly reading one 40-message room; the source and Rustfire bodies differ in raw size, and the same-host client shares CPU and network resources with the server. Record a separate-host, sustained, mixed-user trial before drawing an overall capacity conclusion.

Add `--resources` for sampled peak proportional set size (PSS), process count, and server CPU seconds during full-200 trials; it requires Python `psutil`. The sampler includes Puma's parent and children plus the isolated Redis process for Campfire, and Rustfire's server process. It samples PSS every 500 ms. CPU seconds cover the Go client's warmups and measured requests, while throughput and latency cover only the measured interval. The client process is excluded from both apps' resource figures.

For a browser-style message POST, run `python bench/paired_message_create.py`. The disposable probe sends the same form to each app, checks HTTP 200 and Turbo Stream content type, compares parsed response structure and static values, and verifies the saved message ID, client ID, and text. Add `--sample-dir /tmp/create-samples` to retain both raw responses.

For Open Graph presentation parity, run `python bench/paired_link_preview.py`. It posts the same five rich messages to disposable instances and compares the complete parsed presentation subtree, including a preview-only attachment, duplicate solo URL suppression, X/Twitter URL normalization, and Twitter avatar styling. Add `--read-clients 32 --seconds 10 --campfire-workers 22` to post 40 more solo-preview messages, compare the complete parsed latest-40 page, and measure checked full-HTML reads. The page comparison normalizes generated timestamps, session-specific values and URL origins, and Campfire's optional cached CSRF inputs. Repeat with `--campfire-first` to reverse trial order; add `--sample-dir /tmp/preview-pages` to retain both HTML responses. The timed reader checks status, media type, and message count on every response. Raw bytes still differ, and writes are outside the timed read interval.

For rich-text sanitization, run `python bench/paired_rich_filters.py`. It posts the same seventeen bodies to both disposable apps and compares the full parsed message presentation for disallowed image/table/section tags, allowed address/big tags, safe and unsafe attributes, allowed and rejected URL schemes, safe, unsafe, and malformed data URLs, and ordinary links and formatting. Add `--sweep` for a repeatable 123-case matrix of permitted tags, attributes, URL schemes, data media types, and obfuscated URLs. This is a behavior check, not a throughput measurement.

For a concurrent read/write trial, run `python bench/paired_message_mix.py --clients 32 --seconds 10 --write-rate 10 --campfire-workers 22`, then repeat with `--rustfire-first`. After two read warmups per client, the Go reader signals the measured start and one authenticated writer schedules 100 browser-style Turbo POSTs over about 9.5 seconds. Add `--rich-writes` to cycle bold links, permitted classes, rejected links, lists, time attributes, and rejected images; add `--sockets 100` or `--sockets 1000` to check live delivery and every captured append's parsed markup. Each measured read must return HTTP 200, HTML content type, and 40 rendered message roots; each write must return HTTP 200 and the new message target. The probe verifies identical initial and final parsed message pages, all persisted write IDs and bodies, and the latest 40 IDs. It normalizes generated timestamps and optional nonempty CSRF inputs in the final page. Use `--sample-dir` to retain initial and final pages and the first invalid read if a check fails. Campfire's fragment cache can omit hidden CSRF fields from later HTML reads, so the concurrent read checker does not require a fixed field count. This workload has one account, one room, one writer, and a local load generator; it does not establish sustained multi-user or maximum WebSocket capacity.

Add `--sockets 100`, `--sockets 500`, or `--sockets 1000` to keep signed room-stream subscribers connected during the same read/write trial. Socket setup and subscription confirmation finish before the Go reader warms and signals the writer. The capture checks each socket receives every `mixed-N` append exactly once with numeric message ID `40+N`, and reports missed, unexpected, and early-close counts. It also compares the parsed markup of every paired append for tag order, attribute names and stable values, and text after normalizing generated timestamps and each server's URL origin. Campfire's fragment cache sometimes includes CSRF inputs in newly broadcast boost forms and sometimes omits them; nonempty CSRF inputs are excluded from this comparison. `--sample-dir` retains the first append and all captured events from each app. This does not compare raw Turbo event bytes or measure per-event delivery latency. The sockets, HTTP clients, and server share a host; these ten-second runs are sampled concurrency checks, not maximum user capacity.

For a broader HTTP mix, run `python bench/paired_message_multi.py --rooms 4 --users 4 --clients 32 --seconds 10 --write-rate 5 --campfire-workers 22` and repeat with `--rustfire-first`. The fixture gives every user a separate authenticated session and membership in every room, with 40 seeded messages per room. The checked Go reader assigns clients evenly across all room/user pairs. One writer per room posts as a different user at the requested per-room rate. It compares each room's initial parsed message page, every measured read's status, media type and 40 message roots, every write's Turbo response, saved creator IDs and bodies, and the final page's latest 40 IDs. Add `--sockets-per-room 100` to subscribe 100 sockets in each room using that room's writer session before reader warmup. Every socket must receive each room's expected append once, and the captured event IDs must match the saved database rows. The probe compares all captured append markup for parsed tag order, attribute names, stable values, and text after normalizing generated timestamps, each app's independently assigned message IDs and URL origin, and Campfire's intermittent nonempty CSRF inputs. `--sample-dir` retains the per-room event arrays for diagnosis. Use `--rooms 8 --users 8 --clients 64 --write-rate 3` for the second sampled point. Each app runs serially with disposable SQLite and isolated Campfire Redis. Socket setup is excluded from the timed HTTP interval. This workload does not compare raw event bytes, measure per-event delivery latency, write attachments, or establish sustained capacity.

Add `--resources` to sample CPU time and peak proportional set size (PSS) during measured reads and writes; this requires `psutil`. The Rustfire total includes its server process. The Campfire total includes the Puma parent, workers, and isolated Redis, while the Go reader and Node socket clients are excluded from both totals. Socket setup and reader warmup finish before sampling begins. For a longer paired point, use `--rooms 8 --users 8 --clients 64 --seconds 60 --write-rate 3 --sockets-per-room 100 --campfire-workers 22 --resources` and repeat with `--rustfire-first`. The probe keeps all sockets connected and checks 1,440 saved writes and 144,000 deliveries per app. This minute-long same-host workload still does not establish maximum connections or hours-long steady-state capacity.

For the higher-subscriber sweep, keep the same eight rooms, eight users, 64 readers, and three writes per second per room; set `--sockets-per-room` to 250, 500, or 1000 for 2,000, 4,000, or 8,000 total subscribers in 60-second trials. Use 2000 for the 16,000-subscriber ten-second boundary probe. Repeat each point in both app orders. If either app's writers finish after the measured read interval, the probe still checks persistence, every socket delivery, and all paired append markup, then prints its final JSON and exits nonzero. Inspect `writes.deadline_met`, `writes.max_elapsed_s`, and each room's `elapsed_s` in that JSON. A missed writer deadline means that scheduled write rate was not sustained within the measured interval; it does not imply lost deliveries. The read rate and p95 always cover the fixed interval; write p95 includes writes that complete later.

The source Campfire repository includes `test/performance/chatter.js` for WebSocket fanout. For equivalent HTTP trials, start each app separately on the same hardware and run:

```sh
go run bench/http.go -base http://127.0.0.1:3000 -cookie 'session_token=...' -room 1 -mode read -clients 32 -seconds 30
go run bench/http.go -base http://127.0.0.1:3000 -cookie 'session_token=...' -room 1 -mode write -clients 32 -seconds 30 -csrf '...'
go run bench/http.go -base http://127.0.0.1:3000 -cookie 'session_token=...' -room 1 -mode write -rich -clients 32 -seconds 30
```

The probe loads `authenticity_token` from the room HTML before write trials unless `-csrf` supplies one; both servers enforce it for authenticated writes. The `-rich` flag sends Trix HTML through Rustfire's sanitizer; use it when comparing rich-text writes. The workload is bounded by the client and SQLite on one machine; it does not by itself establish maximum user scale or WebSocket fanout capacity.

The WebSocket fanout probe uses one authenticated session, subscribes a chosen number of sockets to one room, posts messages, and measures deliveries from POST start to each socket. It exits nonzero for missed deliveries or early disconnects:

```sh
node bench/fanout.mjs --app rustfire --base http://127.0.0.1:3000 --cookie 'session_token=...' --room 1 --sockets 100 --messages 20
node bench/fanout.mjs --app campfire --base http://127.0.0.1:3001 --cookie 'session_token=...; _campfire_session=...' --csrf '...' --room 1 --sockets 100 --messages 20
```

The Campfire mode fetches the room's signed `RoomMessagesChannel` stream name before opening sockets. Obtain the CSRF token from the room HTML. Repeat at increasing socket counts, record server CPU and RSS, and run the load generator on another machine for capacity claims. Campfire's Turbo event bodies are currently much larger than Rustfire's JSON event bodies, so these trials do not represent feature-equivalent fanout work.

For the inline boost controls, run `python bench/paired_boost_controls.py` after building the Rustfire release binary. It starts each app serially on disposable databases with isolated Redis, compares parsed boost-list and editor Turbo frames from both frame and direct GET requests, creates a boost and checks the source-style 302 redirect and saved row, then submits the browser's method-override delete form and checks the 204 response and deletion. This probe checks one user's plain boost flow, not fanout speed or complete room-page parity.

On Linux, high-socket localhost trials can exhaust one source IP's ephemeral ports before either server reaches its own limit. Use `--source-ips 127.0.0.1,127.0.0.2` for 30,000 sockets, or four loopback addresses for 40,000, on **both** apps through the paired probe. For example: `python bench/paired_turbo_fanout.py --operation attachments --sockets 40000 --messages 20 --campfire-workers 22 --source-ips 127.0.0.1,127.0.0.2,127.0.0.3,127.0.0.4`. The probe's delivery deadline is 30 seconds from the first post. Connection setup happens before that clock starts; a local port error is a client limit and invalidates the run.

The paired fixture aligns the seeded user names and avatar timestamps, matches the room name, resets Campfire's message sequence so new posts use the same numeric IDs, and sends the same generated content to both apps. Rustfire's public origin is set to the same canonical value used by Campfire so copy-link attributes can be compared despite their different listen ports. The message, text-attachment, image, and video probes check the same user name and signed avatar URL, numeric ID, message and frame target IDs, day heading, room link, absence of eager boost forms, ordered HTML tags after normalizing void-element closing tags, attribute names, static attribute values, and non-whitespace text. The attachment probe also checks the file and Share/Download controls. The image and video probes fetch each signed representation and require byte-identical PNG or WebP content; PNG dimensions are checked explicitly. Generated timestamps differ because the apps run serially; the probe checks their internal order but does not compare their values. The boost probe checks ordered tags, attribute names and values, and non-whitespace text. Add `--sample-dir /tmp/stream-samples` to keep one received Turbo event from each app for markup comparison; image and video runs also keep each preview file. Without it, samples stay in the disposable fixture directory and are removed after the check.

Add `--check-edit` to a message, text-attachment, image, or video run to fetch the first posted message's edit page from each app. The probe compares the edit Turbo frame's ordered elements, attribute names, static values, and text after normalizing per-session CSRF tokens and request origins. With `--sample-dir`, it keeps the full edit responses beside the stream samples.
