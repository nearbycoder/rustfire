# Benchmark protocol

For signed mention presentation, run `cargo build --release` and `python bench/paired_mention.py`. It starts disposable Campfire and Rustfire fixtures with the same source secret, user names, bio, avatar timestamps, and room. It compares autocomplete SGIDs, parsed message presentation, and searchable plain text after posting bare and embedded-content ActionText attachments, a Trix figure, a duplicate mention, a mention of a nonmember, a signed mention after that member is banned, and User attachments with invalid current and Rails 7 signatures. Campfire's own `Message#mentionees` output is compared with Rustfire's saved recipient rows: the invalid-signature User attachments render and remain searchable but do not become notification recipients. This checks eight mention cases; other editor output and notification paths still need parity checks.

For bot mention webhooks, run `cargo build --release` and `python bench/paired_mention_webhook.py`. The probe adds two bots and local webhook URLs to disposable fixtures, starts Campfire's Resque worker with isolated Redis, and captures each app's outgoing JSON on a local receiver. It requires no shared-room delivery for plain `@bot` text, one equal payload each for signed, duplicate, and Trix-figure attachments, delivery to a bot in a direct room without a mention, and delivery to a peer when a bot posts a signed mention through the API. A bot's own direct-room message produces no webhook to itself. A rendered invalid-signature bot mention produces no webhook. It compares the bot API's full message-list JSON in all three rooms, including rich ActionText mention wrappers, after normalizing timestamps and URL origins. Add `--sample-dir /tmp/mention-json-samples` to retain both normalized JSON files. Unavailable endpoints and sustained delivery remain separate work.

For webhook replies, run `cargo build --release` and `python bench/paired_webhook_replies.py`. The probe uses disposable databases, isolated Redis, one Campfire Resque worker, and a local reply server. It posts six signed bot mentions in sequence and compares outgoing payloads, saved reply IDs and attachment metadata, original attachment bytes, and the complete normalized bot message-list JSON. The cases are 200 plain text, 200 HTML, empty 200 plain text, a 500 plain-text attachment, a 200 PNG attachment, and a 500 response without Content-Type that creates no reply. This is a behavior check for six response shapes; it does not measure webhook throughput, retries, timeouts, or other MIME types.

For webhook timeout, connection failure, and manual retry behavior, run `cargo build --release` and `python bench/paired_webhook_failures.py`. It uses disposable databases, isolated Redis, one Resque worker, and a local receiver that waits beyond both apps' seven-second timeout. The probe requires identical timeout payloads, a matching timeout bot reply and normalized bot message list, then points the bot at a refused local port. Neither app creates a bot reply for that second message; Campfire retains one failed Resque job and Rustfire retains one failed SQLite job. It requeues the failed job through Resque and Rustfire's `webhook-jobs retry` command, respectively, then compares the delivered JSON and retained failure records with `retried_at` set. It does not compare every failure metadata field or other network errors.

For Rustfire's webhook queue, run `cargo build --release` and `python tests/webhook_queue.py`. This seeds 80 bots in a direct room, posts one message to a local receiver that deliberately holds requests open, and requires all 80 deliveries and an empty queue afterward. It then restarts Rustfire with one pending and one expired claimed job, requires both deliveries, and checks that both jobs are removed. One bot is deactivated before restart; its queued webhook still sends and saves a text reply. The probe establishes burst retention and restart recovery for this fixture; it does not compare maximum webhook throughput or all failure semantics with Campfire's Resque worker.

For a matched webhook burst comparison, run `python bench/paired_webhook_burst.py --bots 80 --campfire-workers 8` and `--bots 320 --campfire-workers 8`, repeating each with `--campfire-first`. The script seeds the same bot IDs, direct-room memberships, webhook URLs, message, and 100 ms local receiver delay in disposable Campfire and Rustfire databases. It starts isolated Redis and eight Campfire Resque workers, waits until every worker registers, then times each browser POST through the final receiver response. It requires every outgoing JSON payload to match exactly and checks Rustfire's queue drains. Rustfire uses one process with 64 concurrent webhook slots; Campfire uses one Puma process and the specified Resque workers. The trial measures a short burst on one host, not sustained throughput, retries, or a maximum user count.

For a 30-second paired webhook load, run `python bench/paired_webhook_sustained.py --bots 8 --posts 360 --rate 12 --campfire-workers 22 --timeout 180`, then repeat with `--campfire-first`. The script offers one direct-room message every 1/12 second; each message produces eight outgoing webhook requests to a local receiver that waits 100 ms and returns 204. It starts each app on a disposable database, warms one message before timing, and runs the apps serially with isolated Redis for Campfire. It checks every outgoing JSON payload for exact structural equality, one delivery per bot and message, empty queues, and zero failed jobs. The report includes offered-post schedule lag, delivery count and rate during posting, final drain time, total time, and delivery latency. Campfire uses one Puma process and the specified Resque workers; Rustfire uses one process and 64 webhook slots. The source and receiver share the load-generator host, so repeat on separate hosts and at multiple rates before treating this as a production capacity limit.

For a paired rich-mention bot API read sweep, run `cargo build --release` and `python bench/paired_mention_reads.py --clients 32 128 256 --seconds 10 --campfire-workers 22 --slo-ms 250`, then repeat with `--campfire-first`. The script posts 40 signed-mention messages to each disposable app, requires the bot message-list JSON bytes to match after replacing only the local URL origin and each independently generated creation timestamp, and checks the SHA-256 of every measured response against that app's warmed body. Campfire uses its packaged 22-worker Puma configuration and isolated Redis; the two servers run serially on the same host. `largest_sampled_clients_under_slo` is the largest **tested** client count with zero errors and p95 below the supplied objective. Use `--sample-dir` to retain the raw JSON responses. These short same-host trials do not establish maximum supported users, sustained capacity, or feature parity outside the checked bot API page.

For paired presence behavior, run `cargo build --release` and `python bench/paired_presence.py`. The probe starts both servers on disposable SQLite fixtures, with isolated Redis for Campfire, and checks that each clears a fresh three-connection membership on server startup. It then uses one authenticated Action Cable socket per app. It subscribes to the read channel, sets an unread marker, opens the room over HTTP, and checks that neither the marker nor read-channel traffic changes. It subscribes to two distinct presence identifiers for the same room, checks both read events and saved connection counts, sends an unconfirmed identifier message, refreshes with a new unread marker set, and unsubscribes in sequence. A second socket sequence seeds a stale three-connection record before subscribe, refresh, and unsubscribe; both apps must reset its count to one, one, and zero while preserving the unread marker on refresh and unsubscribe. This is a protocol behavior check for one user and room; it does not measure fanout capacity or all presence timing and reconnect cases.

For unread room broadcasts, run `cargo build --release` and `python bench/paired_unread_events.py`. The probe starts both apps with disposable databases, an isolated Campfire Redis server, and three authenticated Action Cable clients: the message author, a room member, and an outsider. It posts one message each while the member is connected and visible, disconnected and invisible, and disconnected and visible. Each phase checks the author's and member's `UnreadRoomsChannel` payload, absence of an outsider event, and whether the member's unread marker was saved. This checks one room and three membership states; it does not measure fanout throughput or all combinations of notification settings.

Use **the same machine**, room fixture size, number of concurrent clients, request bodies, and duration for both servers. Run a warmup before recording results.
