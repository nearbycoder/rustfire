# Benchmark protocol

Use **the same machine**, room fixture size, number of concurrent clients, request bodies, and duration for both servers. Run a warmup before recording results. Keep the server and load generator on separate machines when measuring high throughput. Record CPU, peak RSS, and response error rate alongside latency and throughput. Test at several concurrency levels and increase until the p95 latency or error rate crosses your service objective.

For the matched-fixture trial in `RESULTS.md`, build Rustfire with `cargo build --release`. Run the pinned upstream Campfire commit with Ruby 3.4.10, its locked gems, Redis, and `RAILS_ENV=production DISABLE_SSL=1` on localhost. The upstream Puma configuration automatically chooses its worker count; leave `WEB_CONCURRENCY` and `RAILS_MAX_THREADS` unset to reproduce the packaged-app baseline. Create the first administrator in each app, then stop both servers and seed disposable databases:

```sh
python bench/seed.py campfire /path/to/once-campfire/storage/db/production.sqlite3 --count 10000
python bench/seed.py rustfire /path/to/rustfire/data/compare.db --count 10000
```

The seed script uses the same text and client message IDs in both databases. It refuses a nonempty message table unless `--replace` is supplied. After a write warmup, restore the original fixture before the measured run. Confirm both servers use SQLite WAL and `PRAGMA synchronous=NORMAL`, and that `GET /rooms/1/messages` returns the latest 40 messages with status 200, before recording throughput.

The source Campfire repository includes `test/performance/chatter.js` for WebSocket fanout. For equivalent HTTP trials, start each app separately on the same hardware and run:

```sh
go run bench/http.go -base http://127.0.0.1:3000 -cookie 'session_token=...' -room 1 -mode read -clients 32 -seconds 30
go run bench/http.go -base http://127.0.0.1:3000 -cookie 'session_token=...' -room 1 -mode write -clients 32 -seconds 30 -csrf '...'
go run bench/http.go -base http://127.0.0.1:3000 -cookie 'session_token=...' -room 1 -mode write -rich -clients 32 -seconds 30
```

The probe loads `authenticity_token` from the room HTML before write trials unless `-csrf` supplies one; both servers enforce it for authenticated writes. The `-rich` flag sends Trix HTML through Rustfire's sanitizer; use it when comparing rich-text writes. The workload is bounded by the client and SQLite on one machine; it does not by itself establish maximum user scale or WebSocket fanout capacity.

The WebSocket fanout probe uses one authenticated session, subscribes a chosen number of sockets to one room, posts messages, and measures deliveries from POST start to each socket. It exits nonzero for missed deliveries or early disconnects:

```sh
node bench/fanout.mjs --app rustfire --base http://127.0.0.1:3000 --cookie 'session_token=...' --room 1 --sockets 100 --messages 20
node bench/fanout.mjs --app campfire --base http://127.0.0.1:3001 --cookie 'session_token=...; _campfire_session=...' --csrf '...' --room 1 --sockets 100 --messages 20
```

The Campfire mode fetches the room's signed `RoomMessagesChannel` stream name before opening sockets. Obtain the CSRF token from the room HTML. Repeat at increasing socket counts, record server CPU and RSS, and run the load generator on another machine for capacity claims. Campfire's Turbo event bodies are currently much larger than Rustfire's JSON event bodies, so these trials do not represent feature-equivalent fanout work.

For a disposable signed-stream comparison, run `cargo build --release` and `python bench/paired_turbo_fanout.py --sockets 200 --messages 10 --campfire-workers 1` with Redis running. Add `--operation boosts` to seed one matching message and measure individual boost append events, or `--operation attachments` to upload small matching text files and measure attachment-message appends. Use `--operation images --image-size 2400x1600` for a generated PNG upload that both apps process into a 1200×800 preview before broadcasting. Use `--operation videos` for a generated 16×16 MP4 and WebP poster, or supply `--video-size 2400x1600` to check a larger poster and `--video-sar 3/2` to check display aspect ratio handling. It uses the pinned Campfire checkout, installed Ruby bundle, and source database required by the other paired probes. The script starts one app at a time, signs in to Campfire, extracts each app's room stream name from HTML, checks that the Turbo action targets exist in each room page, and checks that every socket receives every posted event. It reports average message bytes as well as delivery latency. The apps still differ in serialization and storage side effects, so these are protocol and delivery observations rather than feature-equivalent capacity measurements.

The paired fixture aligns the seeded user names and avatar timestamps, matches the room name, resets Campfire's message sequence so new posts use the same numeric IDs, and sends the same generated content to both apps. Rustfire's public origin is set to the same canonical value used by Campfire so copy-link attributes can be compared despite their different listen ports. The message, text-attachment, image, and video probes check the same user name and signed avatar URL, numeric ID, message and frame target IDs, day heading, room link, absence of eager boost forms, ordered HTML tags after normalizing void-element closing tags, attribute names, static attribute values, and non-whitespace text. The attachment probe also checks the file and Share/Download controls. The image and video probes fetch each signed representation and require byte-identical PNG or WebP content; PNG dimensions are checked explicitly. Generated timestamps differ because the apps run serially; the probe checks their internal order but does not compare their values. The boost probe checks ordered tags, attribute names and values, and non-whitespace text. Add `--sample-dir /tmp/stream-samples` to keep one received Turbo event from each app for markup comparison; image and video runs also keep each preview file. Without it, samples stay in the disposable fixture directory and are removed after the check.

Add `--check-edit` to a message, text-attachment, image, or video run to fetch the first posted message's edit page from each app. The probe compares the edit Turbo frame's ordered elements, attribute names, static values, and text after normalizing per-session CSRF tokens and request origins. With `--sample-dir`, it keeps the full edit responses beside the stream samples.

For a matched room reconnect probe, run `cargo build --release` and `python bench/paired_room_refresh.py --iterations 30` with Redis running. It seeds one unchanged, one edited, and one newly created message into disposable databases, checks each app's Turbo refresh response for the same append/replace selection, and reports response latency and size. It does not assert equal HTML, so the timing is an endpoint comparison only.

For a Rustfire-only direct-room reuse regression check, run `cargo build --release` and `python bench/direct_lookup.py --rooms 10000 --iterations 100`. It creates a disposable 10,000-room fixture, checks startup migration of participant keys, compares the indexed SQL lookup with Rustfire's previous grouped query, then times repeated HTTP reuse requests. It does not compare Campfire or measure concurrent capacity.

For a paired ping-reuse trial, run `cargo build --release` and `python bench/paired_direct_lookup.py --rooms 1000 --iterations 10`, then repeat with `--rooms 10000`. The script requires the pinned Campfire checkout, its locally installed Ruby 3.4.10 and locked production bundle, a source production SQLite database containing one room and two users, and a running Redis server. Paths can be supplied with `--campfire-repo`, `--ruby`, and `--bundle-path`. It copies the Campfire database into a temporary directory, clears its messages, seeds both apps with the same 51 users and four-person direct-room sets, and runs them serially with one HTTP client. It does not modify the source database. Campfire runs with one Puma worker and five threads; Rustfire runs as one process. Both apps return HTTP 302, but they still differ in room-list broadcast work, so this is a core-path comparison rather than a full-parity scale claim.

For a paired user-autocomplete trial, run `cargo build --release` and `python bench/paired_autocomplete.py --users 1000 --iterations 30`, then repeat with `--users 10000`. It uses the same pinned Campfire checkout, Ruby bundle, source database, and Redis prerequisites as the ping-reuse trial, makes disposable user fixtures, and checks that both apps return the same 20 names and IDs. The servers use the same secret, and the probe also checks that signed mention IDs and signed avatar URL paths and versions match. It fetches one linked initials avatar from each app and checks its text and background color. URL origins differ because the servers listen on different ports. This single-client endpoint probe does not establish full-app throughput or maximum user scale.

Add `--clients 1 8 32 --seconds 3` to run a concurrent autocomplete sweep after the sequential probe. Each client keeps its own HTTP connection, checks two warmup responses against the same 20 names and IDs, and checks every measured response against its warmup body. The servers run serially with the same disposable user fixture; Campfire uses one Puma worker with five threads. The Python load generator shares the server host, so its throughput and latency are endpoint observations under this configuration rather than maximum server capacity.

For a paired bot message-list trial, run `cargo build --release` and `python bench/paired_bot_messages.py --messages 10000 --iterations 30 --clients 1 8 32 --seconds 3 --campfire-workers 22`. The script uses the same pinned checkout, Ruby bundle, source database, and a running Redis server. It creates disposable databases containing identical users, one room, one bot, and messages alternating between plain text and simple rich text. It gives each run unique cache versions so Campfire cannot return a fragment from a prior trial. Both servers share the signing secret. It checks that the latest 40 parsed JSON messages are equal after removing URL origins, then measures sequential and concurrent reads. The JSON response bytes still differ in escaping, and the default workload does not cover attachments, writes, live delivery, or full-app capacity.

Add `--include-attachments` to replace every tenth message with a file-only text attachment. The fixture includes matching Active Storage metadata and Rustfire attachment rows, but no file bytes. This verifies the bot message-list JSON for attachment messages; it does not measure or verify attachment downloads or thumbnail generation.

For a paired bot administration check, run `cargo build --release` and `python bench/paired_bot_admin.py` with the same pinned Campfire checkout, Ruby bundle, source database, and Redis. It creates disposable databases, submits matching avatar and webhook forms, compares the displayed room-specific text and upload commands, edits and rotates the bot key, checks the message API, then deactivates the bot. It compares redirect status and path, form fields, persisted state, and API access. It also verifies that an older Rustfire database containing a prefixed bot token migrates without changing its public bot URL. This is a behavior check, not a performance test. Campfire stores uploaded avatar files under its configured local storage directory; the probe removes the files it creates after the run.

For account logo behavior and an optional read trial, run `cargo build --release` and `python bench/paired_account_logo.py --clients 1 8 32 --seconds 3 --campfire-workers 22`. It uses the same pinned checkout, Ruby bundle, source database, and Redis. The probe submits a combined account name, setting, and JPEG logo update, then checks both PNG variants, delete and restore behavior, and the stock fallback for a BMP. It requires byte-identical PNGs and reports response throughput and latency for repeated GETs of the uploaded 512-pixel logo. Each app runs separately with a disposable database on the same host; `--campfire-workers 22` matches the packaged Puma worker count on the measurement host. The trial uses warm cached variants and a load generator on the server host. It does not measure upload processing, memory use, sustained load, or whole-app capacity. The probe removes Campfire files created during the run. Add `--sample-dir /tmp/logo-samples` to keep the four uploaded-logo PNG responses.

For account user administration, run `cargo build --release` and `python bench/paired_account_users.py` with the same pinned checkout, Ruby bundle, source database, and Redis. It uses disposable fixtures with an open and a direct room, checks the account roster's administrator/member divider, then submits matching role updates and a delete. It compares redirect status and path, saved role and status, retained direct-room membership, and the repeated-delete response. This is a behavior check, not a performance or full-page visual comparison.

Add `--users 1100` to check the account-user Turbo Stream pages on a larger fixture. The probe aligns names and avatar timestamps, shares the signing secret, compares the IDs and order in the initial edit response and pages 1–4, and checks the replace/append actions and next-frame URL. It also compares parsed elements, attributes, and non-whitespace text after normalizing session-specific CSRF token values. The pinned Campfire edit response renders all 1,100 users before offering a lazy page-2 frame; the page endpoint itself returns 500, 500, and 100 users.

Add `--clients 1 8 32 --seconds 2 --campfire-workers 22` to time warm reads of page 2. Each client keeps one HTTP connection and runs two fully checked warmup requests; every measured response must still contain 500 rows and the boundary users. Rustfire runs as one process, and 22 Puma workers reproduce the packaged Campfire worker count on this host. The load generator shares the server host and the responses differ in whitespace, byte size, and masked CSRF values. The trial measures this page read, not account editing, upload work, whole-app throughput, memory use, or maximum sustained capacity.

Add `--scramble-timestamps` with at least 41 messages to move the lowest ID to the newest timestamp and the highest ID to the oldest. The probe then compares the latest page plus `before` and `after` pages with Campfire. The fixture uses native Rails SQLite datetime text for Campfire and RFC 3339 for Rustfire; this exercises timestamp pagination independently of ID order.
