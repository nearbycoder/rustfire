# Rustfire

An **in-progress** Rust port of [ONCE Campfire](https://github.com/basecamp/once-campfire). The compatibility target is upstream commit `91d294f4a09f9bbe37f9548959bfcb43645678fb`. This repository is **not yet a 1:1 replacement** and no speed or capacity advantage at feature parity has been established.

## Run

Local builds require the libvips development headers and library. The Docker build installs them in its build stage.

```sh
cargo run --release
# Visit http://127.0.0.1:3000 and create the first administrator.
```

With Docker:

```sh
docker build -t rustfire .
docker run --rm -p 3000:3000 -v rustfire-data:/data rustfire
```

Configuration:

- `RUSTFIRE_ADDR` — bind address, default `127.0.0.1:3000`
- `RUSTFIRE_DB` — SQLite file, default `data/rustfire.db`
- `RUSTFIRE_UPLOAD_DIR` — uploaded files, default `data/uploads`
- `RUSTFIRE_SECURE_COOKIES` — set to `true` when serving over HTTPS
- `RUSTFIRE_PUBLIC_URL` — public origin for invite, device sign-in, and message copy links, for example `https://chat.example.com`; otherwise request Host and the secure-cookie setting determine the origin, with the bind address as fallback when no request is available
- `RUSTFIRE_DISABLE_WEBHOOKS` — set to `true` to suppress outbound bot webhook delivery
- `RUSTFIRE_DISABLE_PUSH` — set to `true` to suppress outbound Web Push delivery
- `RUSTFIRE_VAPID_KEY_FILE` — persistent VAPID private-key path; defaults beside the SQLite database as a `.vapid.der` file. Keep this file when moving or restoring an installation so existing browser subscriptions remain valid. A Campfire import without a supplied source key preserves its keyless state and creates no file.
- `RUSTFIRE_CAMPFIRE_SECRET_KEY_BASE` — optional original Campfire secret key base, used to issue and verify Rails mention, avatar, blob, and device-transfer IDs with Campfire's verifier keys. Keep it configured while imported messages or attachments use those IDs. Rustfire also accepts IDs signed with its own persistent keys.
- `RUSTFIRE_TRUSTED_PROXY_IPS` — comma-separated IPs of reverse proxies that append `X-Forwarded-For`; empty by default. Session IPs and bans use the direct peer unless it is listed here.
- `APP_VERSION` and `GIT_REVISION` — optional Campfire-style response version headers. `X-Version` uses `APP_VERSION`, then `GIT_REVISION`, then `0`; `X-Rev` uses `GIT_REVISION` or an empty value.

The server creates its SQLite schema at startup and enables WAL mode. Run behind a TLS proxy for network use. Back up the database and upload directory together.

Failed bot webhooks can be inspected and requeued from the server host:

```sh
RUSTFIRE_DB=/path/to/rustfire.db target/release/rustfire webhook-jobs list
RUSTFIRE_DB=/path/to/rustfire.db target/release/rustfire webhook-jobs retry 1
RUSTFIRE_DB=/path/to/rustfire.db target/release/rustfire webhook-jobs retry-all
```

Retry creates a new delivery job and keeps the failed record with its `retried_at` time. Repeating a retry creates another delivery, as in Campfire's Resque failure queue.

### Import an existing Campfire installation

Stop Campfire, back up its database and `storage/files` directory, then import into paths that do not exist yet:

```sh
cargo build --release
export RUSTFIRE_CAMPFIRE_SECRET_KEY_BASE='the original Campfire secret key base'
python tools/import_campfire.py \
  --source-db /path/to/once-campfire/storage/db/production.sqlite3 \
  --source-files /path/to/once-campfire/storage/files \
  --target-db /path/to/rustfire/data/rustfire.db \
  --target-uploads /path/to/rustfire/data/uploads
```

The offline importer preserves account settings and styles, user IDs and passwords, session records, bans, rooms, memberships, message IDs and timestamps, the user, room, message, boost, and push-subscription ID sequence high-water marks, original plain-text search content where indexed, boosts, searches, bot webhooks, push subscriptions, file attachments, inline files, images, PDFs, and videos, avatars, and the account logo. Missing search-index rows are rebuilt from rich text or the attached filename; the result reports `reindexed_messages`. It copies local Active Storage bytes into the new upload directory, prepares inline previews with Campfire's sharpening and representative video-frame selection, then renders imported rich text with Rustfire's sanitizer and retains signed mention recipients only while they belong to the message's room. Missing inline-image dimensions are read from the image bytes; conflicting saved dimensions still stop the import. Inline galleries use Campfire's 800×600 signed preview variation; inline TIFFs render as PNG previews, while SVG and BMP remain file attachments. It builds the target in a temporary directory and publishes it only after validation. The source remains read-only. Keep the original secret key base configured when running Rustfire afterward so existing signed mentions, blobs, and session cookies can be verified. Test the imported copy before replacing a production service.

Imported user and bot avatar originals are stored in the avatar directory used by Rustfire's image renderer. The importer preserves their source blob IDs and filenames for signed original-file links, including a blob shared by more than one avatar. Replacing or deleting one avatar retains the shared file while another user still references it.

`python bench/paired_import_roundtrip.py` creates a disposable bot, rich-text message, and file attachment in pinned Campfire, imports the stopped account, and compares the rendered bot list, bot editor, and room page with Rustfire. The sampled signed avatar and attachment paths and original bytes match; complete parsed page structure matches after normalizing generated values. This is a repeatable sample, not a full migration validation.

`python bench/paired_large_import.py` separately seeds 16,230 messages in a disposable Campfire database, imports it, and checks every message page against Campfire. All 406 pages match in ordered IDs, exact ETag and Last-Modified headers, and parsed body structure after generated-value normalization. This covers a large single-room history; the wider migration and full-app capacity remain to be established.

`python bench/paired_large_graph_import.py` distributes 16,000 messages across open, private, direct, and member-only rooms. All 700 pages reachable by an administrator and a member match in ordered IDs, exact validators, and parsed structure after normalization. Five-second, both-order reads across seven user-room targets measured **2.10–2.50×** Rustfire throughput at 32 and 128 clients with zero checked errors. See [the multiroom report](bench/results/large-graph-import-reads.json). This remains a same-host read sample without writes, sockets, or attachments.

On that imported graph, four search pages also match in complete parsed head and body: the administrator cannot find the member-only room's messages, while the member can. Three 100-result search targets measured **1.41–1.80×** Rustfire throughput at 32 and 128 clients in both server orders, with zero checked errors. See [the search report](bench/results/large-graph-import-search-reads.json). These are short, read-only trials.

`python bench/paired_import_graph.py` covers a second migration shape with open, private, and direct rooms, unread memberships, a boost, recent searches, and a push subscription. The imported administrator's and member's room pages, sidebar frames, and search pages match the pinned source after generated-value normalization. The administrator's inaccessible-room redirect also matches; the member can read that room and find its message in search. Saved room and content rows match exactly. A member's private-room post after import preserves Campfire's next message ID and produces matching unread state, room pages, sidebars, and search results. The administrator's subsequent notification-setting cycle matches Campfire, including hiding the private room from only that user's sidebar while retaining room and search access.

On that 16,230-message fixture, five-second checked latest-page trials in both server orders measured **2.53–3.01×** Rustfire throughput for full HTML reads and **10.11–13.49×** for conditional 304 reads at 32 and 128 clients, with zero errors. See [the paired report](bench/results/large-import-message-reads.json). These sampled reads do not establish sustained or whole-app capacity.

With `--extra-messages 38`, the same probe imports and compares a full 40-message room page. Its complete parsed head and body match Campfire after generated-value normalization; the sampled raw HTML documents differ in size.

With the same import fixture, ten-second checked room-page reads at 32, 128, and 256 clients in both server orders measured **2.62–3.35×** Rustfire throughput with lower p95 latency and zero read errors in either app. See [the raw results](bench/results/imported-room-reads.json). This sampled workload does not prove sustained or whole-app superiority.

On the imported 40-message room, the same ten-second, both-order sweep measured **3.06–4.55×** Rustfire throughput with lower p95 latency and zero checked errors in either app. See [the 40-message results](bench/results/imported-room-40-reads.json). This is a sampled room read, not a maximum-scale or full-app claim.

If Campfire has configured VAPID keys, set `RUSTFIRE_CAMPFIRE_VAPID_PRIVATE_KEY` and `RUSTFIRE_CAMPFIRE_VAPID_PUBLIC_KEY` to the original pair before import, even if there are no current push subscriptions. The importer verifies the pair and preserves the public key. These variables are required when subscriptions exist. Without a supplied pair and without subscriptions, the imported account remains keyless like a keyless Campfire source; a new Rustfire account still generates its own key. To enable push later on a keyless import, install a VAPID key file at the configured path and restart Rustfire.

The importer preserves unknown inline image subtypes as file attachments and previews valid `video/*` blobs, matching sampled Campfire behavior. It still stops if a previewable image or video cannot be decoded, if image dimensions conflict with saved metadata, or if it encounters an unknown Active Storage attachment record type. It requires local Active Storage files and a stopped source app for a consistent snapshot. Rebuilt search text still needs parity checks for less common ActionText content. These cases, plus full rich-text rendering and media edge cases, remain migration parity work.

A checked 30-second, four-room plain-message trial with 400 sockets subscribed to eight source-shaped channels showed about 2.12× Rustfire read throughput in both server orders, with all 36,000 expected message appends and unread events delivered per app. A paired six-message room page containing plain, rich, text-file, JPEG, MP4, and PDF messages matched parsed Campfire page sections; five-second checked reads at 32–512 clients showed about 3.2–5.0× Rustfire throughput in both server orders. A paired webhook-reply probe matches ten text, HTML, attachment, timeout, and error-response cases, including an eight-second streamed reply and a 26 MiB attachment with identical saved file bytes and bot API JSON. The apps still produce different response content and side effects outside those checked paths, so these measurements do not establish a speed or capacity advantage at full feature parity.

A separate one-bot text-reply load scheduled 120 rich posts at 24 per second in both server orders. Every webhook and saved reply was checked. With 16 Resque workers and no sockets, Campfire drained replies 3.87–4.47 seconds after posting ended; Rustfire took 0.05–0.06 seconds. With 64 subscribed room-message sockets, both apps delivered all 15,360 expected user-post and bot-reply appends. All 240 post and reply appends captured on one socket matched parsed Campfire markup after normalizing generated values. Rustfire completed the workload in about five seconds, while Campfire took 9.86–10.13 seconds under the tested setup. This is a short sampled workload without push delivery; see the [paired reports](bench/RESULTS.md#paired-text-webhook-reply-load).

The same 64-socket load with alternating indexed plain-text and rich HTML bot replies also saved and delivered every reply in both server orders. All captured post and reply appends matched parsed Campfire markup, and Rustfire finished in 5.05–5.07 seconds versus Campfire's 11.32–12.42 seconds under the tested setup. See the [mixed-reply reports](bench/RESULTS.md#paired-mixed-text-and-html-webhook-reply-load).

In a 30-second mixed-reply run at 15 scheduled posts/s with 64 sockets, both apps saved all 450 posts and replies and delivered all 57,600 expected appends per order. This demonstrates more capacity for the tested rich-text browser-channel mix, while maximum scale, longer steady-state behavior, and complete feature parity remain open.
